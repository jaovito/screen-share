# M1 authorization and encryption proof boundaries

Status: accepted for the experiment, not a beta authorization design · 2026-10-26.

## Context

M1 must prove native capture/encoding and encrypted transport before M2 identity/invitations. A public arbitrary token endpoint or client-supplied identity would open an unauthorized publication boundary. This host is macOS; Windows hardware and the two-PC advancement gate cannot be substituted with browser mocks or compilation.

## Decision

Use an offline trusted-operator command for the bounded M1 experiment. The operator reviews an explicit allowlist of two through eight opaque participant IDs, exactly one publisher. Every invocation creates a new random RTC room and five-minute signed grants: screen-share video only for the publisher, subscribe-only for viewers, no data/audio/admin/recording grants. No HTTP route exposes this operation. Private output files are exclusive creations; neither the signing secret nor tokens are printed.

The media key is independently generated by the publishing client, not the operator/API, and distributed through an established encrypted channel. Browser and future native clients must use the same UTF-8 string representation with the SDK's matching PBKDF2 defaults. Use SDK cryptography, not a custom cipher/protocol. Do not persist keys in a database, browser storage, URLs, or diagnostic logs.

The web receiver is opt-in. It checks the client envelope, configures its actual local E2EE worker before connecting, verifies the connected room/local identity, and subscribes only to the designated publisher's one encrypted screen-share video. It does not acquire local media. Errors, expiry, reconnect attempts, source changes, and unexpected tracks stop reception. This envelope validation does not verify JWT signatures; the SFU verifies signed authorization. An encrypted-track flag is not proof of decoded frames or independent E2EE verification.

Native lifecycle rules live in portable domain/application modules. A trusted monotonic clock and verified authorization snapshots gate media operations. The raw-frame queue holds at most one pending native frame. WGC uses the system consent picker and retains its exact capture item; owned BGRA texture copies never cross JSON/IPC/React. Hardware capture is initially an unwired primitive, not an enabled application feature.

## Alternatives

A permissive demonstration login/token endpoint would conflict with the authorization boundary. Full M2 authentication before transport proof would increase product scope before the media architecture is validated. A browser screen-capture publisher would bypass the selected native Windows architecture; only the automated test fixture uses a synthetic canvas publisher.

## Consequences and advancement

The operator is the M1 trust/authorization authority. This is unsuitable for a public service or automatic membership management. A five-minute JWT does not implement strict self-hosted revocation. Membership changes require stopping the experiment, abandoning the RTC room, and independently redistributing a fresh key to the remaining authorized participants; do not reuse the old room/key or claim transactional epoch enforcement.

The automated transport test uses only a 320×180 synthetic canvas at 5 FPS, one Chromium worker, and an owned limited LiveKit container. It exercises the real browser encryption worker and decoder, including a wrong-key negative case. It is not native encoding, native/browser derivation interoperability, two-PC E2EE, a media benchmark, or proof against a malicious SFU.

M1 remains open until WGC/D3D11 → hardware H.264 → native LiveKit feedback/publication is integrated and validated on actual Windows/GPU hardware and two PCs, including source preservation, Alt+Tab, network pressure, and measured process overhead. M2–M5 advancement remains conditional on PLAN.md gates.
